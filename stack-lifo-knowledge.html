Stack — LIFO Data Structure

A linear, ordered collection where insertion and removal are both restricted to a single end: the top.

O(1)
Push / Pop / Peek — all constant time
LIFO
Last In, First Out — insertion order inverted on removal
O(n)
Space — proportional to number of elements
Core invariant: the element removed next is always the one most recently inserted. No element below the top is accessible until every element above it has been popped.

Overflow / Underflow: Pushing onto a full stack (array-backed, fixed size) causes stack overflow. Popping from an empty stack causes stack underflow. Both must be guarded in production code.

Core Operations

Three primitive operations define a stack's entire interface. Each runs in O(1) time regardless of stack size.

Push — Add an element to the top

function Push(stack, element):
    if stack.size == stack.capacity:
        raise StackOverflowError   // guard: array-backed stacks only
    stack.top  ← stack.top + 1  // advance top pointer
    stack.data[stack.top] ← element  // write element at new top
    stack.size ← stack.size + 1

Line-by-line annotation

LineActionComplexity
Overflow checkPrevents writing past allocated memory. Skipped for dynamic (linked-list) stacks.O(1)
Advance top pointerThe index pointing to the current top of the underlying array is incremented by 1.O(1)
Write elementThe new element is placed at position top. No shifting of existing elements.O(1)
Update sizeMaintains the logical count; not always needed if top index is the source of truth.O(1)

Pop — Remove the top element

function Pop(stack):
    if stack.size == 0:
        raise StackUnderflowError  // guard: cannot pop empty stack
    element    ← stack.data[stack.top]  // read top value
    stack.top  ← stack.top - 1         // retract top pointer
    stack.size ← stack.size - 1
    return element

Line-by-line annotation

LineActionComplexity
Underflow checkAttempting to pop from an empty stack is a logical error; guard before reading.O(1)
Read top valueThe element at index top is copied out before the pointer moves.O(1)
Retract pointerDecrementing top logically removes the element; the memory slot is simply ignored.O(1)
ReturnThe caller receives the removed element — critical for algorithms that process popped values.O(1)

Peek / Top — View without removal

function Peek(stack):
    if stack.size == 0:
        raise StackEmptyError      // guard
    return stack.data[stack.top]   // read top, no pointer change

Line-by-line annotation

LineActionComplexity
Empty checkSame guard as Pop — reading an undefined slot is undefined behavior.O(1)
Return top elementNo mutation occurs. The stack state is identical before and after Peek.O(1)
Peek vs Pop: Peek is a non-destructive read — it answers "what is next?" without committing to removal. Use it when the decision to pop depends on the top value (e.g., operator precedence comparison in expression evaluation).

Click any row to jump to that step.

What this demonstrates

Push operations 1-3 build the stack bottom-up: 10 is at index 0, 20 at index 1, 30 at index 2. The top pointer tracks the last filled index.

Step 4 (Peek) reads stack[2] = 30 without mutating state — the top pointer stays at 2.

Steps 5-7 (Pop) remove elements in reverse insertion order: 30, then 20, then 10. This is the LIFO property made concrete — the first element inserted (10) is the last to be removed.

Key observation: after Pop returns 10, top = -1. The array still holds [10, 20, 30] in memory — but those slots are logically invisible because the top pointer is below index 0. No cleanup is needed unless memory reclamation is required.

Example 2 — Backtracking (Path Exploration)

A stack drives depth-first path search. Each visited node is pushed; when a dead end is reached, nodes are popped to retreat to the last branching point.

Scenario: Explore the path A → B → D → (dead end) → backtrack → C → E (goal). The stack records the current exploration path.

Step-by-step trace

Bottom
top = -1 (empty)
StepOperationReasonStack after
1Push("A")Start at node A["A"]
2Push("B")Move to neighbor B["A","B"]
3Push("D")Move to neighbor D["A","B","D"]
4Pop() → "D"D is a dead end — backtrack["A","B"]
5Pop() → "B"B has no unvisited neighbors — backtrack again["A"]
6Push("C")Try next neighbor of A["A","C"]
7Push("E")Move to E — goal reached["A","C","E"]

Click any row to jump to that step.

Graph structure

        A
       / \
      B   C
      |   |
      D   E  ← goal
  (dead end)

Why this requires a stack

The stack encodes the current path from the start node to the current position. When a dead end is encountered, a Pop instantly retreats to the previous node — the one that still has unexplored neighbors.

This is precisely what the CPU call stack does during recursive DFS: each recursive call pushes a frame, each return pops one. An explicit stack like this replaces recursion with iteration, giving direct control over backtracking.

The final stack state ["A","C","E"] is the solution path — readable bottom-to-top.

Visited set: real implementations pair the stack with a set of visited nodes to prevent re-exploring the same node. The stack handles order; the set handles deduplication.

Example 3 — Balanced Parentheses (Expression Evaluation)

A stack validates whether every opening bracket has a matching, correctly nested closing bracket. The approach generalizes to full expression parsing and operator precedence.

Input string: ( [ { } ] ) — expected result: VALID

Pseudocode

function IsBalanced(expression):
    stack ← EmptyStack()
    open  ← { '(', '[', '{' }
    match ← { ')':'(', ']':'[', '}':'{' }

    for each char in expression:
        if char in open:
            Push(stack, char)         // opening bracket → push
        else if char in match:
            if IsEmpty(stack):
                return INVALID           // closing with nothing open
            top ← Pop(stack)
            if top != match[char]:
                return INVALID           // wrong bracket type

    if IsEmpty(stack):
        return VALID                  // all openers were closed
    else:
        return INVALID                // unclosed openers remain

Why the stack is the right structure: brackets must close in the reverse order they opened — an exact LIFO relationship. No other data structure captures this nesting constraint as directly. The top of the stack always holds the most recent unmatched opener, which is exactly the one the current closer must pair with.
