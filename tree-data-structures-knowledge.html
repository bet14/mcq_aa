Tree Data Structures

A hierarchical data structure where nodes are connected by edges, encoding parent-child relationships.

Core Definition: A tree is an acyclic, connected graph where exactly one node — the root — has no parent, every other node has exactly one parent, and any two nodes are connected by exactly one path.

Binary Tree constraint: Every node has at most 2 children, conventionally labeled left and right. This constraint enables ordered traversal algorithms and makes BST operations efficient.

Inorder Traversal

Visit order: Left subtree → Root → Right subtree. For a BST, produces nodes in sorted ascending order.

Key property: Inorder traversal of a Binary Search Tree always yields keys in non-decreasing order — this is the standard method for BST sorted enumeration.

Traversal Order Diagram

Pseudocode Example 1 — Generic Inorder

Algorithm
Recursive Inorder Traversal
function inorder(node):
    if node is NULL:
        return                        // base case: empty subtree

    inorder(node.left)             // 1. Recurse into left subtree
    visit(node)                    // 2. Process current node
    inorder(node.right)            // 3. Recurse into right subtree

Annotation

StepActionStack effect
inorder(node.left)Dive all the way left before visiting anythingPush frame; recurse deeper
visit(node)Print / collect / process node valueAt current frame
inorder(node.right)Process right subtree after current nodePush frame; recurse right

Complexity

CaseTimeSpace (call stack)
All casesO(n)O(h) — h = tree height
Balanced treeO(n)O(log n) stack depth
Degenerate (linked list)O(n)O(n) stack depth

Pseudocode Example 2 — Inorder for BST Sorted Output

Applied Algorithm
Collect Sorted Keys from BST
function bstSortedList(root) → List:
    result ← emptyList()
    inorderCollect(root, result)
    return result

function inorderCollect(node, result):
    if node is NULL:
        return

    inorderCollect(node.left, result)   // all smaller keys first
    result.append(node.key)             // append current key in sorted position
    inorderCollect(node.right, result)  // all larger keys after

// Example BST:   40
//               /  \
//              20   60
//             / \   / \
//            10  30 50  70
// Result: [10, 20, 30, 40, 50, 60, 70]

Annotation

LinePurpose
result ← emptyList()Accumulator; passed by reference through all recursive calls
inorderCollect(node.left, result)Ensures all keys less than node.key are appended first
result.append(node.key)BST property guarantees this key is larger than all previously appended
inorderCollect(node.right, result)All keys greater than node.key appended last

Complexity

MetricValueNote
TimeO(n)Each node visited exactly once
Space (stack)O(h)Recursion depth = tree height
Output listO(n)Stores all n keys

Preorder Traversal

Visit order: Root → Left subtree → Right subtree. The root is always the first node visited.

Key property: Preorder captures the structural "shape" of a tree — the output sequence fully encodes the tree and can reconstruct it. Used for copying trees and serializing tree structure.

Traversal Order Diagram

Pseudocode Example 1 — Generic Preorder

Algorithm
Recursive Preorder Traversal
function preorder(node):
    if node is NULL:
        return                        // base case

    visit(node)                    // 1. Process root FIRST
    preorder(node.left)            // 2. Recurse into left subtree
    preorder(node.right)           // 3. Recurse into right subtree

Annotation

StepActionWhy first?
visit(node)Process node before any childGuarantees root appears before all descendants in output
preorder(node.left)Dive into left subtreeAll left descendants visited before right
preorder(node.right)Dive into right subtreeRight subtree visited last

Complexity

CaseTimeSpace
All casesO(n)O(h)

Pseudocode Example 2 — Tree Serialization

Applied Algorithm
Serialize Tree to String (Preorder + NULL markers)
function serialize(root) → String:
    parts ← emptyList()
    serializeHelper(root, parts)
    return parts.join(",")

function serializeHelper(node, parts):
    if node is NULL:
        parts.append("#")           // NULL marker preserves structure
        return

    parts.append(node.val)         // visit root FIRST (preorder)
    serializeHelper(node.left, parts)
    serializeHelper(node.right, parts)

// Tree:    1
//         / \
//        2   3
//       / \
//      4   5
// Output: "1,2,4,#,#,5,#,#,3,#,#"
// The # markers make deserialization unambiguous

function deserialize(data) → Node:
    tokens ← data.split(",")
    index ← 0
    return buildTree(tokens, index)

function buildTree(tokens, index):
    if tokens[index] == "#":
        index ← index + 1
        return NULL
    node ← newNode(tokens[index])
    index ← index + 1
    node.left  ← buildTree(tokens, index)
    node.right ← buildTree(tokens, index)
    return node

Annotation

ElementRole
"#" markerEncodes NULL children — without this, the string is ambiguous and reconstruction fails
Preorder orderRoot is always first token; enables top-down reconstruction in deserialize
index (shared)Single advancing pointer through token array; must be passed by reference

Complexity

OperationTimeSpace
SerializeO(n)O(n) output string + O(h) stack
DeserializeO(n)O(n) reconstructed tree + O(h) stack

Postorder Traversal

Visit order: Left subtree → Right subtree → Root. The root is always the last node visited.

Key property: Children are always visited before their parent. This makes postorder the natural traversal for operations that must process children before the parent: deletion, computing subtree sizes, evaluating expression trees bottom-up.

Traversal Order Diagram

Pseudocode Example 1 — Generic Postorder

Algorithm
Recursive Postorder Traversal
function postorder(node):
    if node is NULL:
        return                        // base case

    postorder(node.left)           // 1. Recurse into left subtree first
    postorder(node.right)          // 2. Recurse into right subtree
    visit(node)                    // 3. Process root LAST

Annotation

StepImplication
postorder(node.left)Entire left subtree is fully processed before current node is touched
postorder(node.right)Entire right subtree processed before current node
visit(node)Safe to process parent only after both children are done — critical for deletion or aggregation

Complexity

CaseTimeSpace
All casesO(n)O(h)

Pseudocode Example 2 — Expression Tree Evaluation

Applied Algorithm
Evaluate Arithmetic Expression Tree (Bottom-Up)
// Expression tree for (3 + 4) * (2 - 1):
//        *
//       / \
//      +   -
//     / \ / \
//    3  4 2  1

function evaluate(node) → Number:
    if node is a leaf (no children):
        return node.value              // base case: numeric operand

    leftVal  ← evaluate(node.left)   // evaluate left operand subtree
    rightVal ← evaluate(node.right)  // evaluate right operand subtree

    // now apply operator stored at this node
    switch node.operator:
        case '+': return leftVal + rightVal
        case '-': return leftVal - rightVal
        case '*': return leftVal * rightVal
        case '/': return leftVal / rightVal

// Call trace:
// evaluate(*) calls evaluate(+) and evaluate(-)
//   evaluate(+) → evaluate(3)=3, evaluate(4)=4 → returns 7
//   evaluate(-) → evaluate(2)=2, evaluate(1)=1 → returns 1
// evaluate(*) → 7 * 1 = 7   ← final answer

Annotation

PatternWhy postorder?
Leaf returns literal valueBase case — no children to evaluate
Recurse left, then right, then operatorAn operator node cannot compute its result until both operand subtrees return values
switch node.operatorInternal nodes hold operators (+, -, *, /); leaves hold operands

Complexity

MetricValueNote
TimeO(n)Each operator/operand node visited exactly once
Space (stack)O(h)Recursion depth equals expression tree height

Binary Tree Properties

Classification of binary trees based on structural completeness and balance.

Tree Type Comparison

TypeDefinitionHeightExample use
Full Binary Tree Every node has 0 or 2 children (never 1) O(n) worst, O(log n) best Expression trees
Complete Binary Tree All levels filled except possibly the last; last level filled left-to-right O(log n) Binary heaps (priority queues)
Perfect Binary Tree All internal nodes have exactly 2 children; all leaves at same level O(log n) Theoretical analysis baseline
Balanced Binary Tree |height(left) - height(right)| ≤ 1 for every node (AVL definition) O(log n) AVL trees, Red-Black trees
Degenerate Tree Every internal node has exactly 1 child (a linked list in tree form) O(n) Worst case for naive BST insertions

Visual: Tree Type Diagrams

Height and Complexity Impact

Tree TypeHeightSearch (BST)Insert (BST)Space
Perfect / BalancedO(log n)O(log n)O(log n)O(n)
CompleteO(log n)O(log n)O(log n)O(n)
DegenerateO(n)O(n)O(n)O(n)
The degenerate case is why balancing matters. Inserting sorted data into a naive BST degenerates it into a linked list, destroying the O(log n) guarantees. Self-balancing trees (AVL, Red-Black) maintain height O(log n) through rotations.

Applications

Where tree structures and their traversals appear in real systems.

Expression Trees

Compilers parse arithmetic/boolean expressions into binary trees. Inorder traversal reconstructs infix notation. Postorder traversal evaluates the expression bottom-up (operands before operators).

Decision Trees (ML)

Classification and regression trees. Each internal node splits on a feature; each leaf holds a prediction. Preorder traversal mirrors the prediction algorithm — evaluate root condition, recurse into the matching child.

File System Hierarchy

Directories form an n-ary tree (not strictly binary). Preorder traversal walks top-down (Unix find). Postorder traversal enables safe directory deletion — children deleted before parent.

Binary Search Tree (BST)

Inorder traversal of a BST yields sorted keys in O(n). BST supports O(log n) search, insert, delete on balanced trees. Basis for database index structures (B-trees generalize BSTs).

Heap (Priority Queue)

A complete binary tree satisfying the heap property. Efficiently supports O(log n) insert and O(log n) extract-min/max. Used in Dijkstra's algorithm, heap sort, task scheduling.

Syntax Trees (AST)

Abstract Syntax Trees represent program structure. Compilers, linters, and transpilers traverse ASTs (usually preorder or postorder) to analyze, optimize, or transform source code.

Traversal-Application Mapping

TraversalKey ApplicationsWhy this order?
Inorder BST sorted output, infix expression generation, kth-smallest element L → Root → R respects BST ordering: left keys < root < right keys
Preorder Tree copying/serialization, prefix expression, directory listing, AST printing Root first — encodes structure; parent always appears before children
Postorder Tree deletion, expression evaluation, directory size computation, dependency resolution Children before parent — safe to free/process parent only after all children done

Key Takeaways

Consolidation of core concepts, complexity bounds, and decision heuristics.

Traversal Summary

TraversalOrderFirst visitedLast visitedTimeSpace
Inorder L → Root → R Leftmost leaf Rightmost leaf O(n) O(h)
Preorder Root → L → R Root Rightmost leaf O(n) O(h)
Postorder L → R → Root Leftmost leaf Root O(n) O(h)
All three traversals have identical asymptotic complexity: O(n) time (every node visited once) and O(h) space (maximum call stack depth equals tree height h). The difference is purely in visit order.

Height Impact on Performance

Balanced tree — h = O(log n)Optimal
Degenerate tree — h = O(n)Worst case

When to Use Each Traversal

Inorder — whenever sorted order matters: BST validation, range queries, sorted output.
Preorder — whenever the parent must be processed before children: copying, serialization, prefix notation, top-down algorithms.
Postorder — whenever children must be ready before the parent: deletion, bottom-up evaluation, subtree aggregation, dependency resolution.
